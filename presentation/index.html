Feature Deep-Dive

The Substitution Engine — step by step

1

Faculty Dispatches Request

Faculty taps a session in their timetable and selects "Request Substitution". A reason is optionally added. Request is saved to the database.

2

System Ranks Candidates: P1 → P2 → P3

P1 — Free during that slot and teaches the same subject  |  P2 — Free and in the same department  |  P3 — Any free, eligible faculty

3

Candidates Receive Inline Notification

The request appears inside the candidate's timetable slot. They see session details and can Accept or Reject directly from the grid — no navigation required.

4

PostgreSQL Trigger → Instant Resolution

The moment any candidate accepts, a database trigger fires: it locks the request, assigns the substitute, and marks all other candidates' entries as closed. Student timetable updates automatically.

Under the Hood

Security & Data Architecture

🔒 Row-Level Security (RLS)

Every Supabase table enforces role-based access at the database layer — not just the API. Even if the API is bypassed, data stays protected.

🎓 Admin sees all data
👤 Faculty sees only their own sessions + involved subs
📚 Student sees only their section's published timetable

🗄️ Key Database Objects

Table timetable_sessions — all scheduled slots
Table substitution_requests + candidates
RPC resolve_substitution_request() — SECURITY DEFINER
Trigger tr_assign_sub_on_accept — auto-assigns on accept
View faculty_view_all_published — scoped timetable
🔑 Authentication: Role passkeys — no user accounts required. Admin, Faculty, and Students identified by known shared keys. Zero signup friction
What Makes It Stand Out

Technical Highlights

🧮

CP-SAT Constraint Programming

Replaces brute-force scheduling. OR-Tools CP-SAT solves what would be an NP-hard combinatorial problem in seconds, with provably zero hard conflicts.

⚡

Database Trigger for Instant Resolution

The substitution assignment happens inside the database via a trigger — not the frontend or API. Atomically consistent, race-condition free.

🛡️

SECURITY DEFINER RPC

Elevated DB operations (cross-role writes) run via a stored procedure with its own permissions — maintaining RLS everywhere else without exceptions.

🎯

Inline Timetable Actions (UX)

Substitution requests, acceptances, and rejections are surfaced directly inside the timetable grid slot — no modals, no page navigation, minimal friction.

Engineering Journey

Key Challenges & How We Solved Them

Challenge

Race Condition on Accept

Two faculty could accept simultaneously, creating a double-assignment.

Solution

PostgreSQL trigger + atomic RPC with row lock ensures only one wins.

Challenge

RLS Blocking Cross-Role Updates

Faculty accepting a request needed to write to rows they don't "own" under RLS.

Solution

SECURITY DEFINER stored procedure runs with elevated rights, scoped safely.

Challenge

Student View Lagging Behind

Admin showed "Accepted" but student timetable still showed "Pending".

Solution

Fixed trigger to update timetable_sessions + client sweep polls all open requests.

Challenge

Timetable Generation Conflicts

Manual scheduling couldn't satisfy all constraints simultaneously.

Solution

CP-SAT solver encodes all constraints mathematically and guarantees feasibility.
